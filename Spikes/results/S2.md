## S2: gapless loop with AVSampleBufferDisplayLayer and two AVAssetReaders

Run 2026-09-17, macOS 27.0 (26A428), Apple M5, built-in 120 Hz display. Engine: `Shared/LoopEngine.swift`.
Compressed samples go from `AVAssetReaderTrackOutput` (no output settings, video track only) straight into
the layer's `AVSampleBufferVideoRenderer`; a second reader is opened ahead of time; each pass is enqueued
with its timestamps shifted so the layer sees one endless timeline.

### How "presented frames" were measured

`AVSampleBufferVideoRenderer.displayedPixelBuffer()` (macOS 14.4+) returns the picture the layer has on
screen. A 4 ms timer polls it and times every change. Three things had to be learned first:

- The call returns a new `CVPixelBuffer` object every time, so object identity is useless (it reported
  760 "changes" for 570 frames). The `IOSurface` behind it is stable for as long as that picture is up.
- The decoder's output is a compressed pixel format; reading its bytes crashes. To identify *which*
  picture is up (`probe=2`), it is scaled to a 96x54 BGRA buffer with `VTPixelTransferSession` and hashed.
  The test clips (`testsrc2`) differ in every frame, so pass 0 numbers the file's frames.
- The window server throttles a window that is covered, or on another Space, to about one update per
  second. The first long runs "stalled" for that reason alone. The harness window now floats on all
  Spaces, and the probe ignores the time it is not visible and reports how many seams it really watched.

`AVVideoPerformanceMetrics` (the renderer's own count of dropped frames) is recorded too, but it did not
see the defect below, so it cannot be the test on its own.

### The defect the probe found, and its cause

First version of the engine: timestamps perfectly continuous by its own bookkeeping (seam step 1.000
frame), renderer reporting 0 or 1 dropped frames in 750, and yet at every seam one picture stayed up for
two frame durations, with the whole presentation slipping one frame later per pass:

```
seam 1 (t=5.000):  #120@-0.030  #121@+0.038!  #122@+0.070 …      (#120 = last frame, #121 = first frame)
seam 2 (t=10.000): #120@+0.002  #121@+0.070!  #122@+0.102 …
seam 3 (t=15.000): #120@+0.038  #121@+0.102!  #122@+0.138 …
```

Controls: a single 20 s pass of a clip with the same encoder settings had no such gap, so it is the
looping; a 60 fps HEVC clip slipped by one of *its* frames per pass, so it is per pass, not per second;
every reader hands out the same `CMFormatDescription` object, so it is not a decoder reconfiguration.

Cause: for a 150-frame clip `AVAssetReaderTrackOutput` vends 154 buffers.

```
buffer 0    numSamples 0  pts 0       attachments: EditBoundary
buffer 1    numSamples 1  pts 0       attachments: ResetDecoderBeforeDecoding      <- first frame
…
buffer 150  numSamples 1  pts 4.9667                                               <- last frame
buffer 151  numSamples 0  pts invalid attachments: DrainAfterDecoding
buffer 152  numSamples 0  pts invalid attachments: PostNotificationWhenConsumed
buffer 153  numSamples 0  pts 5.0     attachments: EmptyMedia, PermanentEmptyMedia
```

The engine skipped buffers with an invalid PTS, but the last marker has a valid one (the track's
duration). It was enqueued and counted as a frame, so "end of the pass" came out one frame late, and the
engine's own seam metric, which counted it too, read a perfect 1.0. Fix: a frame is a buffer with at
least one sample and a data buffer; everything else is left out. (Also: the first buffer of a reader is a
marker, so "enqueue the first frame before starting the clock" has to skip to a real one.)

After the fix, same clip, same probe:

```
seam 1 (t=5.000):  #119@-0.034  #120@-0.002  #121@+0.034  #122@+0.066 …
seam 2 (t=10.000): #119@-0.034  #120@-0.002  #121@+0.034  #122@+0.066 …
seam 4 (t=20.000): #119@-0.034  #120@-0.002  #121@+0.034  #122@+0.066 …
```

The reader marks the first frame of every pass `ResetDecoderBeforeDecoding`. Stripping it from passes after
the first, or leaving it, made no measurable difference (5 loops each, no missing pictures either way).
The engine strips it, because a reset at an IDR of the same stream buys nothing.

A second defect of the same kind showed up on the clip with B-frames, at the first seam only: the last
picture held for three frame durations (`max presented gap 3.00 frames, over 1.5: 1`, pictures
`#104@-0.030  #105@+0.070!`; from the session's output, the JSON of that run was not kept). That file's first
frame sits at media time 0.0667 s, which ffmpeg's edit list moves to 0 (`raw/s2-reader-buffers.txt`: `pts
1024/15360 … out-pts 0.0`). The reader leaves PTS in media time and carries the edit list as a separate
*output* time, and the layer honours the output time: so pass 0, enqueued as vended, played two frames
earlier than the retimed copies of the later passes. Fix: stamp every pass with output time plus offset.
After it, 20 loops of that clip have no gap over 1.20 frame durations.

Evidence kept: `raw/s2-before-marker-fix.json` (the probe trace of the first defect; read it with
`scripts/seam-pictures.py 150`), `raw/s2-reader-buffers.txt` (`scripts/dump-reader-buffers.swift` on both
clips), and the final runs below.

### Results

Pass criterion: 200 consecutive loops of a 5 s clip, no gap between presented frames over 1.5 frame durations.

Final runs, on the build that includes every fix above and the code-review fixes (20260917152856).
Window: `scripts/s2-window-suite.sh`, output `raw/s2-window-suite.txt`, per-run JSON `raw/s2-window-*.json`.
Extension: `Livepaper config mode=video video=… probe=1`, log lines in `raw/s2-in-extension.log` (third run,
starting 15:31).

| Host | Clip | Loops (seams watched) | Largest presented gap | Gaps over 1.5 | Renderer dropped | Result |
|---|---|---|---|---|---|---|
| Window | 1080p30 H.264 | 200 (199) | 1.32 frames | 0 | 0 / 30000 | PASS |
| Extension (desktop surface) | 1080p30 H.264 | 200, still clean at 260 | 1.44 frames (1.11 at a seam) | 0 | 0 / 32441 | PASS |
| Window | 1080p30 H.264 with B-frames and an edit list | 20 (19) | 1.32 | 0 | 0 / 3000 | pass |
| Window | 1080p30 H.264, audio track longer than video | 20 (19) | 1.09 | 0 | 0 / 3000 | pass |
| Window | 1080p60 HEVC | 20 (19) | 1.24 | 0 | 2 / 6000 | pass |
| Window | 4K60 HEVC | 20 (19) | 1.68, in the middle of pass 0 | 1 | 2 / 6000 | seams clean; one late frame |

The same suite had been run twice before on earlier builds (`raw/s2-window-suite-before-review-fixes.txt`,
and the two earlier extension runs in `raw/s2-in-extension.log`): the 30 fps rows came out the same; the
60 fps rows had 3 to 4 gaps of 1.68 in one run and none in another, always mid-pass, never at a seam. In the
first extension run two gaps of 1.56 appeared only after loop 240, while a 4K60 window test was running
next to it. So at 60 fps a frame is now and then shown one refresh late when the machine is busy; that is
load, not the loop, and it is M8's soak test that should put a number on it.

What "PASS" rests on: the displayed-picture probe (4 ms poll, so ±4 ms per interval; at 30 fps the limit of
1.5 frame durations is 50 ms, at 60 fps it is 25 ms and a single late 120 Hz refresh, 8.3 ms, already reads
as about 1.7), with the window visible for every seam counted. Nobody watched the loops.

### CPU and energy, against AVPlayerLooper

`scripts/energy-suite.sh`, output in `raw/energy.txt`. `top -stats cpu,power`, six 5 s samples after a 15 s
warm-up, one run each, on battery with Low Power Mode off, System Settings closed, built-in 3024x1964
120 Hz display. "Power" is top's unitless energy-impact score (`powermetrics` would give watts but needs
root). The machine was not idle: WindowServer alone was at 22 % CPU with nothing playing, so its column is
only good for rough differences.

| Case | Player process | VTDecoderXPCService (all) | WindowServer |
|---|---|---|---|
| Nothing playing (extension shows the colour) | 0.0 % / 0.0 | | 22.1 % / 34.9 |
| Window, sample-buffer engine, 1080p30 H.264 | 1.3 % / 2.4 | 1.4 % / 1.5 | 24.4 % / 36.2 |
| Window, AVPlayerLooper, 1080p30 H.264 | 1.4 % / 2.6 | 1.6 % / 1.7 | 28.9 % / 40.9 |
| Window, sample-buffer engine, 4K60 HEVC | 2.4 % / 3.4 | 3.3 % / 3.4 | 40.4 % / 53.0 |
| Window, AVPlayerLooper, 4K60 HEVC | 2.5 % / 3.5 | 3.7 % / 3.8 | 36.7 % / 48.1 |
| Extension, desktop surface, 1080p30 H.264 | 1.6 % / 2.6 | 1.6 % / 1.7 | 35.4 % / 47.6 |
| Extension, desktop surface, 4K60 HEVC | 2.7 % / 3.6 | 3.5 % / 3.6 | 45.1 % / 56.5 |

(CPU % / power score.) The two engines cost the same within the noise of one run; the sample-buffer engine
is not more expensive, which was the worry. The cost that matters is compositing: a full-screen 4K60
wallpaper adds roughly 20 points to WindowServer's score, about three times what decode and the engine add together.

### Energy budget for 4K60 (the M8 threshold)

For one display playing a 4K60 HEVC wallpaper with the desktop visible, measured the same way on the same
class of machine, M8 passes when:

- the extension process stays at or under **4 % CPU** and a power score of **5**;
- `VTDecoderXPCService` (summed) stays at or under **5 % CPU** and a power score of **5**;
- WindowServer's power score is no more than **25** above its score with the wallpaper paused, taken in
  the same session;
- and all three return to their paused levels within 5 s of the desktop being fully covered, or the
  display sleeping.

These are today's numbers with about 40 % headroom, from a single run on a machine that was in use. M8
should re-measure on an idle machine, with `powermetrics` for watts, before holding anyone to them.
