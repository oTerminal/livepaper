## S1: where the library can live

Run 2026-09-17 on macOS 27.0 (26A428), build signed selfsigned / plain / S1 entitlements, in /Applications.

### (a) `~/Library/Application Support/LivepaperSpike/` + read-only home-relative exception: PASS

Entitlement on the extension: `com.apple.security.temporary-exception.files.home-relative-path.read-only = ["/Library/Application Support/LivepaperSpike/"]`.
It is not a restricted entitlement: the extension launched with it under an ad-hoc and under a self-signed signature, with no provisioning profile.

```
13:37:22.621 Livepaper          s1: wrote a-1080p30-h264.mp4 and config generation 1 to ~/Library/Application Support/LivepaperSpike in 0.00 s
13:38:14.274 LivepaperExtension s1: NSHomeDirectory = ~/Library/Containers/app.livepaper.spike.extension/Data; real home = ~
13:38:14.275 LivepaperExtension s1: location a (Application Support + exception): READABLE, 2 entries, config 78 bytes
13:38:14.291 LivepaperExtension extension: config generation 1 mode video video a-1080p30-h264.mp4 from ~/Library/Application Support/LivepaperSpike
13:38:14.302 LivepaperExtension extension: surface 4B9207C2… display 1 now on a-1080p30-h264.mp4 (generation 1)
```

No `deny(` line from the kernel sandbox for the extension and no tccd prompt request in the log (a prompt
could not have been seen: the session had no view of the screen). Readable again under every later build
(`READABLE` lines for builds 144629, 144855 and 145059 in `raw/installs-recovered-1446-1452.log`) and under
an ad-hoc signature (build 144629, 14:46:40): the exception is a path in the sandbox profile, not tied to
the signature. Log: `raw/s0-s1-recovered-1325-1340.log`. Inside the sandbox the home
directory APIs return the container, so the real home comes from `getpwuid`.

Darwin notifications, both directions, from inside the sandbox:

```
13:39:28.506 LivepaperExtension extension: configChanged received (app -> extension notification works)
13:39:28.510 LivepaperExtension extension: surface 4B9207C2… display 1 now on b-1080p30-h264.mp4 (generation 2)
             Livepaper          app: heartbeat from extension: generation 2, loops 15 (extension -> app notification works)
```

The heartbeat carries 64 bits of state (`notify_set_state` in the extension, `notify_get_state` in the app): no file needed.

### (b) the extension's own container, written by the app: FAIL without a Team ID

Launched through LaunchServices (`open -n -a … --args s1 write=b …`) so TCC attributes the write to Livepaper:

```
13:40:10.973 Livepaper s1: write to ~/Library/Containers/app.livepaper.spike.extension/Data/Documents/library FAILED after 0.01 s: NSCocoaErrorDomain Code=513 "You don’t have permission to save the file “library” …"
13:40:10.971 sandboxd  kTCCServiceSystemPolicyAppDataDetailed denied by TCC for Livepaper
13:40:10.971 sandboxd  TCC authorization request fails: kTCCErrorDomain Code=9 "kTCCServiceSystemPolicyAppDataDetailed access requires indirect object have an associated app bundle"
13:40:10.971 kernel    (Sandbox) sandboxd rejected approval request from Livepaper for kTCCServiceSystemPolicyAppData (~/Library/Containers/app.livepaper.spike.extension/Data/Documents): denied
```

The write is refused in 10 ms, which leaves no room for a prompt. Log: `raw/s1-b-launchservices.log` (and the
`s1: write … FAILED` line in `raw/s0-s1-recovered-1325-1340.log`). Phosphene gets away with this route because its app and
extension share a Team ID, which exempts them from App Data protection.

Trap: the same write run from a terminal succeeds, because TCC then holds the terminal (here Conductor,
which has Full Disk Access) responsible. That is what `raw/s1-b.log` and `raw/s1-b.app.txt` show: the first,
invalid attempt, in which the write worked and the extension played from its container. Test this only
through `open`.
