# M7: system integration

Wire the app to macOS and to the doors that are not the window: the login item, hotkeys, the `livepaper://` scheme, the `livepaper` tool, rotation, onboarding (which makes Livepaper the system wallpaper), leaving and diagnostics. Importing stays in the app's window: Services, Open With, the Dock and menu-bar drops and an `import` verb were built and then removed (As built). It continues lane A after M5-engine.md and wires what lane B's M6-screens.md draws. See `docs/roadmap.md` (Import, Rotation, System integration, Selection, Quit, First run) and records 0001 to 0004, 0003 above all.

## Rules

- Code goes in `LivepaperSystem` (MainActor: login item, hotkeys, the store, rotation, the socket, diagnostics), `LivepaperCore` (the pure `Command` grammar), `App/`, `CLI/` and `Resources/Samples/`.
- No permission-gated API (`docs/roadmap.md`): no Accessibility, Screen Recording, Automation or Full Disk Access. Hotkeys are Carbon, System Settings is opened by URL and never driven, the store is a file in the user's Library. Wallper's Apple event to Settings costs a TCC prompt (`docs/research/wallper.md`).
- The app is the only writer of the manifest, `render-state.json` and the store (record 0002). Every door becomes a `Command` the app model runs; nothing else, the CLI included, writes a file.
- One type touches the store, at selecting and leaving only (record 0003): never on a launch, never on Quit, nothing when Livepaper is already selected, never a whole-file swap.
- The login item is `SMAppService.mainApp`: no LaunchAgent plist, no helper, the row showing real status and never intent. A hotkey never animates the interface (M3-design-system.md); the crossfade is content and still runs.
- Vocabulary is `CONTEXT.md`'s; "Selection" is Livepaper being the system wallpaper, what a display shows an **assignment**. Test-first at the seams below with an injected clock, a seeded RNG and fakes. CI is macos-26 / Xcode 26.

## The grammar

`livepaper://<verb>?<key>=<value>`. The verb is the host. A path, fragment, port, user name, or a key the verb does not take, is a rejection.

| Verb | Keys | Does |
|---|---|---|
| `set` | `wallpaper` or `playlist` (a UUID in the library), `display` (a UUID or `all`) | Assigns. An ID the library does not hold is refused |
| `pause`, `resume`, `next` | `display` (default `all`) | The transport actions; `next` moves on a display with a playlist |
| `mute`, `unmute` | none | Global mute (its state is M6-screens.md's) |
| `library`, `settings` | none | Opens the library window, or Settings |
| `diagnostics` | none | Clipboard from the app, returned over the socket, printed by the CLI |
| `status` | none | Socket only: host status, displays and assignments, the library's IDs and names, pause and mute, as JSON |

Wallpapers are named by ID, never by path; no verb names a file, imports or runs anything. Any web page can open the scheme, so what a link can ask is what the popover's buttons do. Importing is done in the app's window alone: the library window's drop zone and Import…, and onboarding's first card; `import` is an unknown verb to the scheme, the socket and the tool.

The CLI uses the socket, not the scheme: LaunchServices reports only that the app took a URL, so there is no reply and no exit code, and an XPC Mach service needs a launchd job the app lacks. With none there it opens the app by `NSWorkspace.urlForApplication(withBundleIdentifier:)` and retries; `set` also takes a name, resolved through `status`. M7 confirms and records three things: that the socket path fits `sockaddr_un`'s 104 bytes, else it moves to the temporary folder; whether `eventHotKeyExistsErr` covers a combination another process holds; and where a session's start comes from (`utmpx`, else `kern.boottime`).

## Diagnostics and the restart button

M6-screens.md leaves the diagnostics export here, so M7 adds its rows to Settings on M3-design-system.md's components: "Copy diagnostics" copies the report, "Save…" uses a Save panel, `livepaper diagnostics` prints it.

- **Holds**: the app's and extension's versions and builds; macOS and hardware; whether the bundle is translocated; the self-check line and `RenderHostStatus`; per display the UUID and assignment by ID; pause rules, pauses and mute; the login item's status and intent; the store's shape check (Desktop entries, how many name Livepaper, whether the kept copy exists); the extension's log lines.
- **Never**: a wallpaper's name, any path, the user's name, the Steam account's name (M12-workshop.md), the store's file lists, another process's log. Lines are redacted of home paths and importable file names, and telemetry stays none.
- **Log lines** come from `/usr/bin/log show` on the extension's subsystem, 10 minutes, 200 at most; `OSLogStore.local()` is understood to need an entitlement this app cannot have; M7 confirms that, and that a plain user gets lines at all. Wallper logs nothing, so its reports carry no evidence (`docs/research/wallper.md`).
- **"Restart wallpaper service"** (`StatusLine`, wired by M6-screens.md) calls `RenderHost.recover(.restartAgent)` through `allowAgentRestart`; the line shows `.working`, the result, or when it can next be tried.

## As built

What M7 decided or found on the way, for M8-hardening.md, M9-release-engineering.md and M10-1.0.md. Names are quoted from the code; "here" is the development Mac, macOS 27.0, one display.

### What was confirmed on this Mac

- **The socket fits.** The socket is `LibraryLocation.commandSocket`, here `~/Library/Application Support/Livepaper/command.sock`: 72 bytes, 73 with the NUL, against `sun_path`'s 104. A path that does not fit, measured as the file system spells it (accents decomposed), moves to `$TMPDIR/livepaper-command.sock` (`commandSocket(fallback:)`); the app and the tool work it out the same way.
- **`eventHotKeyExistsErr` across processes.** Only an exclusive registration against an exclusive one fails. A holder that is not exclusive gives a second process `noErr`, with or without `kEventHotKeyExclusive`; an exclusive holder gives `noErr` without it and `eventHotKeyExistsErr` with it. Within one process a second registration always fails. So `Hotkeys` registers everything exclusively. ⌘Space, ⌘Q, ⌃Space and ⌘⇧3 all answered `noErr` (free); only ⌘Tab answered taken, the Dock holding it exclusively. The recorder says only what `RegisterEventHotKey` said, so a user can take ⌘Q.
- **A session's start** (`SessionStart`) comes from `utmpx`: the running console `USER_PROCESS` on line `console`, here 33 s after `kern.boottime`; else `kern.boottime`, which cannot see a logout and login without a restart.
- **The login item.** `SMAppService.mainApp.status` reads `notFound` for a copy never registered, so `LoginItem` shows `notFound` as off until a registration is answered with it, and shows `notFound` while translocated. After the user took the item out of Login Items (selected, then −), `sfltool dumpbtm` held no record of the app at all and the row read off; the next launch's reconcile kept the intent off (intent on, not registered, the same copy: the user's choice). Livepaper's own `unregister()`, when leaving, leaves a record marked `[disabled, allowed, notified]`, which System Settings does not list.
- **The store here** was a 725-byte binary property list: `SystemDefault` and `AllSpacesAndDisplays` each with Desktop, Idle and `Type "individual"`, `Displays` and `Spaces` empty. Both Desktop entries named `app.livepaper.Livepaper.WallpaperExtension` with configuration "livepaper" and `EncodedOptionValues` a 54-byte `{values: {}}` property list, which the production entry writes too; the Idle entries named an Aerial. No store with Spaces of their own exists here, so the 24-entry, 11-Space fixture was built in the real shape (`Tests/LivepaperSystemTests/Fixtures/README.md`).
- **Log lines.** `log show` gave the extension's lines to this user, an administrator, without `sudo`, and `OSLogStore.local()` opened without an entitlement here, contrary to this spec's understanding. `log show` is still what is used. A standard account was not tried.
- **The `livepaper` tool ships inside the app**, at `Contents/Helpers/livepaper`: in `Contents/MacOS` it would collide with `Livepaper` on a case-insensitive disk. The app target depends on `livepaper-cli` and copies it in an Embed Dependencies phase with CodeSignOnCopy, so it is signed as `app.livepaper.cli` before the app is sealed (its Info.plist section, `CREATE_INFOPLIST_SECTION_IN_BINARY`, names it); `codesign --verify --strict` passes on the app. M9's signing order signs it as nested code before the app.

### Selecting, leaving and the host

- **Selection's restart** is not held to the ten-minute gap: it is what makes the edit take effect, and it comes once per select or leave. It is recorded in the shared `AgentRestartStore` before its signal, and the host reads that record at activation and before every automatic restart, so its own ladder does not restart the agent again within ten minutes of it.
- **Not selected is not silence.** WallpaperAgent launches the extension only while Livepaper is the system wallpaper, so a user who chose another hears nothing from it. Before an automatic restart for silence the host reads the store through `WallpaperStore`'s shape check, and only reads it (`HostEvent.readForRestart`, answered in the same turn): named nowhere, the status is `.notSelected`, no restart is made, and the ladder waits for a heartbeat, a wake or an activation; named, or unreadable, the ladder goes on as M5 left it. So an ordinary launch that is not selected restarts nothing (record 0003), and onboarding logs one store write and one restart, both Selection's.
- **The popover's line** says "Livepaper is not your wallpaper", shortened from "…not the wallpaper in System Settings" to make room, with "Open System Settings…" beside it as Restart sits beside its line (`statusLineOffersWallpaperPane`: not while an import or Restart has the line). The store is not touched. A host status has one set of words, `RenderHostStatus.words`, which the line and `livepaper status` ("Status: …") share, and one name, `RenderHostStatus.name`, for the logs, the socket and the diagnostics.
- **Leaving**, from Settings' confirmation (which now says the login item goes), runs `Selection.leave()`, turns the login item off and keeps that intent, records `LeftLivepaper`, and quits as Quit does, holding the stopped state. With no usable copy the pane opens and the app still quits; should System Settings not open either, an alert gives the words first.
- **Pause All pauses in place** (changed on 2026-09-24 at the product owner's request, after Pause All jumped to the poster; record 0003 amended). It writes no stopped state: `RenderState.make(…isPausedAll:…)` marks every display `userPaused`, so the extension does exactly what it does for a display's own pause (`decision … pause.user`), with no new schema and no change there: a video holds its current frame and keeps its decoder, a scene stops its display link on its last picture and keeps the scene, and Resume All, a state made without it, resumes at once with a display's own pause kept. The host is not deactivated, so its heartbeat, its ladder and the metrics probe carry on, and a change made while paused all reaches the displays paused, as it would a display paused on its own. The cards (`nowPlaying(…isPausedAll:…)`) and the status line read "Paused"; the log says `app: pause all, render state <n> pauses every display`. While the library cannot be read, Pause All does nothing, as its button is disabled then. Still not remembered, so a relaunch plays; the stopped state is Quit's alone.
- **`MacSystemServices`** (`App/Model/MacSystemServices.swift`, assembled by `SystemWiring.mac(host:)`) is the real `SystemServices`. The login item's status is read again whenever the app becomes active or a window becomes key; `reconciling` runs at every launch that is not translocated, and the answered intent is kept when it differs; each flip of the switch keeps what was asked, never while translocated. `Hotkeys` is made at launch from `AppState.hotkeys`, and each change is kept by the model, the one writer (`SystemServicesOwner`). Presses reach the app delegate as a stream and run inside `withoutAnimation`: Pause or Resume All, Next Wallpaper on every display showing a playlist in one change, Mute or Unmute, Open Library.

- **Doors** (`App/Shell/Doors.swift`). `application(_:open:)` takes links. A file LaunchServices still hands over, from `open -a Livepaper <file>`, is counted and left (`LaunchServicesHandover`, `door: 1 file handed over and left: importing is done in the app's window`). A link is parsed by `EntryPoint.urlScheme`; a rejection is logged by its kind (`door: livepaper:// link refused: a “wallpaper” that is not a UUID`) and goes no further; `diagnostics` puts the report on the clipboard.
- **Commands** (`AppModel+Commands.swift`) run through the window's own actions. A command that arrives before the launch has read the library and the displays waits for it, 10 s at most (`readyWait`), then is refused with "Livepaper is still starting; try again in a moment", so the tool exits 1 rather than wait for ever. A wallpaper, playlist or display that is not there is refused in `CommandRefusal`'s words; `next` with no display showing a playlist is refused; `pause` and `resume` without a display are Pause All and Resume All.
- **Log lines never hold a path, a user name or a source file's name.** A command is logged as `command: <what> from <door>` by IDs, then `done` or `refused: <reason>`; an error by its kind (`LogWords.kind(of:)`: `CommandServerError.kind`, else the domain and code and the POSIX error under them); the socket by its folder (`socket: listening, in the library folder`). M6's lines that name a wallpaper are M6's convention and stay.
- **The socket** is opened once the launch has read the library, in the wired run only, and closed at quit before the model stops. The fakes run opens none; `Tools/pr-media/fakes.sh door socket <url>` runs a command as the socket would and logs the reply line.

### Rotation, diagnostics and Restart

- **Rotation** (`AppModel+Rotation.swift`, `RotationSchedule`). The driver is made at launch when the library could be read, with the system sleep sensor (the fakes' `FakeSleepSensor`, "Sleep and Wake" in the Fakes menu), launched with `SessionStart.current()` when the displays are first known and before the first render state, told of every state change, display change, Pause All and Resume All, and stopped at quit. Decided on the way: a display showing a playlist with no rotation on record starts its interval when first seen; a rotation dated later than now (the clock went back) counts from now; a wake leaves alone a display that rotated in the last 10 s (`wakeAfterRotation`); the timer is nudged past `nextRotation`'s own interval check, since a date plus an interval does not always come back as the same interval. On fakes: a wake moved the Studio Display's playlist on, Pause All logged "no tick due", Resume All "counts from" the resume.
- **Diagnostics** (`AppModel+Diagnostics.swift`). Redacted of the home folder, `NSUserName()`, `NSFullUserName()`, the Steam account's name, every wallpaper's and library file's name and the files imported this session. The store section is `WallpaperStore`'s shape check, counts only, and tells an unreadable store from one of a shape this build does not know. Settings' General pane has a Diagnostics section: Copy Diagnostics and Save… (a Save panel, `Livepaper Diagnostics <date> at <hh.mm.ss>.txt`), with a spinner while the report is made (about 2 s, most of it `log show`) and "Copied" or "Saved" for 5 s. No new design-system component was needed.
- **Restart** (`ServiceRestart`, Core). The line says "Restarting the wallpaper service" while `recover(.restartAgent)` runs, then "Waiting for the wallpaper service" for up to `HeartbeatTiming.standard.grace`, or "Restarted recently; try again at <time>" when the host refused (its `lastAgentRestart`, new to `RenderHost`, did not move) or the service did not answer; the host's status has the line again when the service answers or that time comes. `FakeRenderHost` keeps the ten-minute gap too, and takes `agentRestartTime` to restart.

### Found on screen

- **Show Desktop from a hot corner left a covered display paused** until the next app switch. M5's sensor read the window list only on events, and Show Desktop posts none: no app activates and no Space changes, as the windows slide aside or come back. A read would not have helped either. While Show Desktop is on, WindowManager lists a window of its own over the whole display at level 18, which the desktop shows through, and `coveredDisplays` counted it as covering. The windows moved aside stay in the on-screen list at new bounds, a 12 pt sliver left at the display's edge (a display-sized window at y 1157 of 1169). Now WindowManager's windows are ignored as the Dock's are, and one over a whole display means Show Desktop (`isShowingDesktop`). While the rule is on and the last read found a display covered or Show Desktop on, `CoveredDisplayReader` reads the list every second. The read that finds Show Desktop over is followed by the two event reads, since its window leaves about 0.1 s before the windows are back. With nothing covered, nothing is read until the next event, as before. A read takes about 2 ms, most of it in the window server. The real sensor, with a click-through window over the display and Show Desktop asked for by `open -a "Mission Control" --args 1`, reported the display uncovered 1.1 s and 0.35 s after the request, over two runs, and covered again 1.15 s and 1.27 s after the second: the windows take 0.1 s to start moving, and a read may come 0.1 s late so that the system can fire it with other timers. Stage Manager was not tried (it is off here): should WindowManager keep a window over the whole display there, the list would be read every second while the rule is on. The product owner confirmed the hot corner on screen with this build.
- **The tool opened an old build.** With the app not running, `livepaper status` asked LaunchServices for `app.livepaper.Livepaper` and got one of six registered copies, an old build in another checkout, which it opened. The tool now opens the app it ships inside (`enclosingApp(ofTool:)`, from its own path with links resolved), and asks LaunchServices only when it runs from outside an app.
- **⌘Space never reaches the recorder.** Spotlight takes it before the app sees a key, so recording ⌘Space opens Spotlight and the recorder says nothing, although `RegisterEventHotKey` answers free for it.
- **Developer notes.** `lsregister -f` on the installed app, like a build swap, kills the running extension, and the host's ladder then waits out the ten-minute gap from the last restart. Every `make build` registers its DerivedData copy with LaunchServices and pkd, which may then choose it over the installed one on the next agent restart: before a swap, unregister and delete the other copies (`pluginkit -r`, `lsregister -u`) at a moment the ladder may restart the agent.
